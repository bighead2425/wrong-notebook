# 「题目 → AI → 知识点标签」链路：现状解剖与重设计方案

> 写于 2026-10-31，对应代码 `3e573e3`（数学人教版词表那次提交）。
> 用途：给外部大模型评审用。所有判断都标了文件与行号，可以逐条核对，不是印象。

---

## 0. 一句话结论

现在这条链路的问题**不是"提示词写得不好"，也不是"词表不准"**，而是三件事被塞进了同一次生成：

> 一次调用里，AI 要同时干：①把图片转成文字 ②把题做对 ③判学科 ④判错因 ⑤在几百个近似名字里挑 3 个标签。

而且它挑完之后**只交回名字、不交回位置**，服务端拿名字去反查——而词表里 38 个知识点跨册重名，反查必然撞车。

所以再怎么调提示词，都只是让这五件事互相抢注意力。要动的是**协议**（交回什么）和**分工**（谁在什么时候做）。

---

## 1. 现状：题目是怎么交给 AI 的

### 1.1 入口有四个，行为不一致

| 入口 | 文件 | 是否带学科 | 说明 |
|---|---|---|---|
| 首页单题拍照 | `src/app/page.tsx:304` | 通常**不带** | `notebookId: initialNotebookId \|\| autoSelectedNotebookId \|\| undefined`，第一次拍照时两个都为空 |
| 某个错题本内新增 | `src/app/notebooks/[id]/add/page.tsx:246` | 带 | 学科确定 |
| 批量流水线 | `src/components/batch-pipeline.tsx:912` | 通常**不带** | 从首页进批量时 `defaultNotebookId` 为空 |
| 已有题重新分析 | `src/app/error-items/[id]/page.tsx:545` | 视情 | — |

**关键事实**：最常见的那条动线（首页拍照）恰好是"学科未知"的那条。

### 1.2 服务端怎么定学科

`src/app/api/analyze/route.ts:90-101`：

```
notebookId 有值 → 查 Notebook.subject → 得到 math/chinese/...
notebookId 为空 → subjectName = null
```

### 1.3 学科为空时发生了什么（重要 bug）

`src/lib/ai/openai-provider.ts:215`（azure / gemini 三份完全一样，分别在 188、199 行）：

```ts
const subjectKey = subject ? (SUBJECT_KEY_BY_NAME[subject] ?? 'math') : 'math';
const tagTree = await getTagTree(subjectKey, grade ?? null);
```

**学科未知 ⇒ 默认按数学拉标签树。**

于是：一张语文阅读题的照片，AI 拿到的清单是"五年级上 / 四年级上 的数学知识点"，而它还要在 `<subject>` 里判出"语文"。

结果有两种，都不好：
- 它老实判"语文"，但清单里全是数学 ⇒ `knowledge_points` 写 `UNMATCHED` ⇒ 标签全丢；
- 它顺着清单判成"数学" ⇒ 存进数学本，整条记录错位。

这条不是"可能"，是代码字面量 `: 'math'`。线上任何一次"从首页首次拍照"，走的都是这条路。

### 1.4 提示词里到底给了 AI 什么

`src/lib/ai/tag-service.ts:139` 的 `getTagTree()`：取**每个叶子的父节点**作为"单元"，把它的子节点作为"知识点"。

而词表层级是四层（`scripts/rebuild-system-tags.ts:48-108`）：

```
册（根：五年级上）
 └ 章（第一单元 小数的再认识和加减法）
    └ 节（小数的意义与数位）
       └ 知识点（叶：小数的意义 / 小数的数位与计数单位 / 小数的读写）
```

`getTagTree` 取的是**叶子的父节点 = 节**。也就是说：

> **册和章在提示词里彻底消失了。**
> AI 看到的是 52 行「■ 小数的意义与数位 / 小数的意义 / 小数的数位与计数单位…」，却不知道这 52 行分别属于哪一册、哪一章。

`src/lib/ai/prompts.ts:450-459` 的渲染结果长这样：

```
**数学知识点（按单元/板块分组）**

■ 小数的意义与数位
    小数的意义 / 小数的数位与计数单位 / 小数的读写
■ 小数的大小比较
    小数的大小比较 / 小数末尾添0去0
...
```

**这就是"AI 在按字面相似度猜"的物理原因**：它拿不到"这题属于第几单元"这个先验，只能看哪个名字长得像。

### 1.5 AI 交回来的是什么

`prompts.ts:136-138` 要求：

```
<knowledge_points>
知识点1, 知识点2, 知识点3
</knowledge_points>
```

**只有名字，没有位置。**

提示词里明明写了"先判断属于哪个单元/板块（■ 开头的行），再只在该行下列出的知识点里选"——**要求它做了定位，却不要求它把定位结果交出来**。它内部可能真的先选了「第五单元 多边形的面积」，但输出里只剩三个字符串。

这是整条链路最贵的一次信息丢失。

### 1.6 落库时怎么处理这个名字

`src/app/api/error-items/route.ts:190-232`（POST）：

```ts
let tag = await prisma.knowledgeTag.findFirst({
    where: { name: tagName, subject: subjectKey, OR: [{isSystem:true},{userId:user.id}] },
});
if (!tag) {
    const parentId = await findParentTagIdForGrade(finalGradeSemester, subjectKey);
    if (!parentId) { unmatchedTags.push(tagName); continue; }   // 好：不建
    tag = await prisma.knowledgeTag.create({ data: { name: tagName, ..., parentId }});
}
```

两个问题：

**(a) `findFirst` 按名字取第一个命中的。** 而词表里跨册重名 38 处（实测，见下表）：

| 知识点 | 出现在几册 |
|---|---|
| 轴对称图形 | 二年级上 / 三年级下 / 五年级上 / 八年级上 |
| 三角形内角和 | 四年级下 / 五年级上 / 八年级上 |
| 长度单位换算 | 二年级下 / 四年级下 / 五年级上 |
| 面积单位换算 | 三年级下 / 四年级下 / 五年级上 |
| 小数的读写 | 四年级下 / 五年级上 |

一个五年级孩子的「轴对称图形」题，`findFirst` 会命中**二年级上**那条（插入顺序在前）。题挂对了名字，挂错了册——统计、出卷、复习进度全跟着偏。

**(b) 新名字只能挂到"册"上。** `findParentTagIdForGrade()`（`src/lib/tag-recognition.ts:4`）返回的是**顶层节点（册）**。所以 AI 自造的名字（例如带括号补充的"等式的性质（两边同乘…）"）会被挂成「五年级上」的直接子节点，和"第一单元"平级。树里从此多一层野节点。

### 1.7 静默丢标签

`route.ts:383` 把 `unmatchedTags` 回给前端，但**前端没有任何地方读它**（全仓 `grep unmatchedTags` 只有三处，都在后端）。

所以"这道题的标签一个都没存上"这件事，用户在界面上**完全看不见**。

### 1.8 人工纠错时没有候选

`src/components/correction-editor.tsx:420` 用的是 `TagInput`（`src/components/tag-input.tsx`）。它的行为是：**必须先打出几个字，才会去 `/api/tags/suggestions?q=...` 查**。

家长想把"小数的加法"改成词表里的"小数加法"，得先猜出词表用了哪个字。猜不对就自己造一个——这正是那 60 个野生根标签的来源。

### 1.9 改标签这条路径是漏的

`src/app/api/error-items/[id]/route.ts:700-725`（PUT）：

```ts
let tag = await prisma.knowledgeTag.findFirst({
    where: { name: tagName, OR: [{isSystem:true},{userId:user.id}] },   // 少了 subject
});
if (!tag) {
    const parentId = await findParentTagIdForGrade(contextGrade, subjectKey);
    tag = await prisma.knowledgeTag.create({ data: { ..., parentId } });  // parentId 可能是 null
}
```

两处与 POST 不一致：

- 查重**没有 subject** ⇒ 数学的「函数」会命中别的学科的「函数」；
- `parentId` 为 null 也照建 ⇒ **又造根节点**（POST 那条已修，PUT 这条没修）。

所以"漏网的根标签"还会持续产生。

## 2. 根因归纳（只有三条）

### 根因一：任务耦合——五件事共用一次生成

`<question_text>` 要逐字转录（含 LaTeX、表格），`<answer_text>` 和 `<analysis>` 要把题做对，`<subject>` 判学科，`<mistake_category>` 判错因，`<knowledge_points>` 选标签。

从模型的角度，这是一次"长输出、多目标"的生成。标签排在第 2 位输出（`prompts.ts:136`），而转录和解析排在它后面。模型是自回归逐个 token 生成的 ⇒ **标签是在它还没写出任何解析之前就定下来的**，写完解析也不会回头改。

这是"标签选得像但不准"的结构性原因：**没有第二次机会**。

### 根因二：协议里没有位置，只有名字

名字是**不唯一**的标识（38 处重名），也是**不稳定**的标识（AI 会改写、加括号、合并）。用名字反查，等于用一个既会撞车又会漂移的键做主键。

而词表本来是有稳定 id 和完整路径的。**信息在 AI 那一侧是有的（它看过 ■ 行），只是没被要求交出来。**

### 根因三：没有反馈，也没有锁

- AI 选错 → 人改 → 没有任何记录回流。同一类题下次还错。
- 人工确认过的标签没有"锁定"标记，下次重新分析会被 AI 覆盖（对比：错因已经有 `mistakeCategorySource`，标签没有对应的东西）。

## 3. 方案空间

先说清楚约束，不然方案没法比较：

| 约束 | 含义 |
|---|---|
| C1 不能要求家长多操作 | "录 100 道"是核心场景，每次录入最多容忍 0–1 次点击 |
| C2 不能让孩子填难度 | 已定：难度由行为推断，不让人填 |
| C3 NAS 内存紧 | 容器空闲约 200MB，不能起向量库/本地模型 |
| C4 教材会变 | 词表每年可能微调，方案不能把词表结构焊死 |
| C5 图片是唯一输入 | 没有独立 OCR（前端压缩 → 直接送视觉模型），所以"先 OCR 再检索"这条路不存在 |

### 方案 0：只修 bug（1 小时）

- 学科未知时**不默认数学**：给"学段内 2–3 科"的合并树，或直接不给清单、只让它说 UNMATCHED。
- PUT 补 subject、补 null 保护。
- 前端把 `unmatchedTags` 显示出来。
- `getTagTree` 的 unit 从"节"上提到"章"（恢复层级）。

**能解决**：语文题被迫用数学清单、PUT 造根节点、静默丢标签。
**不能解决**：名字反查撞车、一次生成五件事、没有反馈。

成本 ≈ 半天。**无论选哪个方案，这几条都该先做**——它们是止血，不是方案。

### 方案 A：一次调用，但交回"坐标"（1 天）

把输出协议从"名字列表"改成"路径 + 名字"：

```xml
<knowledge_points>
<kp book="五年级上" unit="第五单元 多边形的面积" section="平行四边形的面积" name="底和高的对应"/>
<kp book="五年级上" unit="第五单元 多边形的面积" section="平行四边形的面积" name="平行四边形的面积"/>
</knowledge_points>
```

服务端按 `book + section + name` 三段定位，命中就用 id；定位不到再退回"仅按名字"（并标记 `matchedBy=name`，进待确认队列）。

**优点**
- 改动面小：只改提示词模板 + 解析器 + 落库函数，不动前端动线。
- 立刻消灭"跨册撞车"——因为册次是 AI 明确说出来的。
- 顺带得到"这道题属于哪一章"这个**对人有用**的信息（可以显示在题目详情页，比一堆标签好懂）。

**缺点**
- 仍然是一次生成、五件事抢注意力，选点准确率提升有限。
- 依赖模型老老实实抄路径，可能抄错册次（尤其小学跨年级复习卷）。
- 输出变长，token 略增。

**适用**：作为"协议升级"的地基。**不管后面走不走两阶段，这个协议都该先落地。**

### 方案 B：两阶段——先定位，再检索，最后在候选里选（3–5 天）

把"生成任务"改成"检索 + 排序任务"。

**第 1 轮（轻量，不带清单）**

输入：图片。
输出只要四行：学科、册次（或学段）、章/单元、这题在考什么（自由文字，20 字内）。
不要求解题、不要求转录、不要求标签。

**服务端检索（不是模型干的事）**

拿第 1 轮的"学科 + 册次 + 章/单元"去词表里**定位到 1–3 个章**，把这些章下的知识点全部取出（通常 10–30 个）。再用第 1 轮的自由文字做字面/别名匹配，排序取前 20–40 个作为候选集。

这一步是纯代码，可单测，结果可解释——**出了问题能查出是哪一步错的**，而不是"模型又抽风了"。

**第 2 轮（纯文本，不再发图）**

输入：第 1 轮转录不出题干——所以这轮只给"题目的简短描述 + 候选清单（带编号）"。
输出：编号列表（1–3 个），以及"都不合适"这个选项。

因为候选集只有 20–40 个、且都属于同一章，这一轮的准确率和第 1 轮定位质量高度相关，而对模型的"知识广度"要求大幅下降。

**优点**
- 每一步都可测、可回归：定位准确率、检索召回率、排序准确率，三个独立指标。
- 候选集小 ⇒ 模型不需要"从 184 个里挑 3 个"（九年级实测：七上到九下共 184 个知识点）。
- 第 2 轮不发图 ⇒ 便宜、快。
- 出问题时知道该修哪一步。

**缺点**
- 两次调用，总延迟增加（估计 +3~6 秒，取决于模型）。
- 第 1 轮定位错了，第 2 轮再准也没用（误差放大）⇒ 需要"候选集为空/置信度低"时的降级路径：退回方案 A 的一次调用。
- 需要新建"别名表 / 检索层"这套基础设施。

### 方案 C：异步归类（2 天，可独立于 A/B）

录入时**不等标签**：先存题（题干、答案、解析、错因、原图），标签状态记为 `pending`，后台任务慢慢归类；前端在题目卡片上显示"归类中"。

**优点**
- 录入速度立刻变快（家长最在意的是"拍完就能下一张"）。
- 归类失败可以重试、可以批量重跑、可以人工批量确认——不阻塞主流程。
- 为 B 的两阶段争取了时间预算（后台跑两轮完全没问题）。

**缺点**
- 要多一张任务表 + 一个后台执行器（项目里已有 `batch` / `tasks` 页面，可复用）。
- 短期内会出现"题在、标签还没到"的状态，UI 要能表达。

### 方案 D：不做预筛，做"归并 + 待确认队列"（1 天，止血）

不追求"第一次就对"，只保证"错了能看见、能一次改对"：

- 名字归一化（去空格、全半角、括号补充剥离）后做相似度匹配，>0.85 自动归并到已有节点；
- 归并不了的进"待归类"队列，标签页里集中展示"AI 造的词 / 词表里可能对应的词"两列，一次点选确认；
- 确认后记 `source=human` 并锁定，AI 之后不再覆盖。

**优点**：成本低，把"静默丢标签"变成"可见、可批量处理"。
**缺点**：不提高首次准确率，只是把返工变便宜。

### 对比表

| | 改动面 | 首次准确率 | 可诊断性 | 延迟 | 风险 |
|---|---|---|---|---|---|
| 方案 0 修 bug | 极小 | 低→中 | 低 | 不变 | 极低 |
| 方案 A 交坐标 | 小 | 中 | 中 | 不变 | 低 |
| 方案 B 两阶段 | 大 | **高** | **高** | +3~6s | 中（第 1 轮误差放大） |
| 方案 C 异步 | 中 | 不影响 | 中 | **-0**（更快） | 低 |
| 方案 D 归并队列 | 中 | 低 | 中 | 不变 | 低 |

## 4. 我的建议：0 → A → D → B，分四次落地

不是"选一个"，因为它们解决的是不同层的问题：

1. **方案 0（半天）**：先止血。学科未知不再默认数学；PUT 补 subject 与 null 保护；`unmatchedTags` 显示出来；`getTagTree` 恢复到"章"这一层。
2. **方案 A（1 天）**：把协议改成"交坐标"。这一步的副产品是**每道题都知道自己属于哪一章**——这比标签本身对家长更有用。
3. **方案 D（1 天）**：加"待归类"队列和 `source=human` 锁。让错误可见、可批量修。
4. **方案 B（3–5 天）**：等前三步稳定、而且**线上攒够一批真实样本**（至少 100 道带人工确认标签的题）之后再做两阶段。没有这批样本，B 的两步准确率都没法验证，等于盲改。

第 4 步之前值得先做一件小事：**给每道已确认标签的题记下 `tagSource`（ai / human / merged）**。这就是 B 的验收基准。

### 为什么不直接上 B

因为 B 的价值完全取决于"第 1 轮定位"的准确率，而这个准确率**现在没有任何数据**。先上 B，等于用两次不确定的调用换一次不确定的调用，还可能更差。

A 和 D 会顺手把这批数据攒出来。

## 5. 如果走方案 A，数据契约长这样

```ts
// AI 输出（XML，保持现有风格，不引入 JSON）
<knowledge_points>
<kp book="五年级上" unit="第五单元 多边形的面积" section="平行四边形的面积" name="底和高的对应" />
<kp book="五年级上" unit="第五单元 多边形的面积" section="平行四边形的面积" name="平行四边形的面积" />
</knowledge_points>

// 解析后
interface TagRef {
  book?: string;     // 册 / 学段，可空
  unit?: string;     // 章
  section?: string;  // 节
  name: string;      // 知识点
}

// 落库结果
interface ResolvedTag {
  tagId: string | null;
  ref: TagRef;
  matchedBy: 'path' | 'name' | 'alias' | 'none';
  confidence: number;
}
```

`matchedBy` 是给"待归类队列"用的：只有 `path` 和 `alias` 算高置信，`name` 要人确认，`none` 直接进队列。

**一个必须守住的规矩**：`matchedBy !== 'path'` 时**不许自动新建节点**。宁可挂着不归类，也不要再造野节点——这条 POST 已经这么做了，要把它提升成全局规则，PUT 也照办。

## 6. 还没想清楚的地方（希望被指出）

1. **第 1 轮的"册次"到底该不该让 AI 判？** 用户主页已填 `gradeTerm`（五年级上），理论上大部分题就是本册。但复习卷会混入上学年。是"默认本册 + AI 只在明显不符时才改"，还是"总让 AI 判"？前者省事但会把上学年的题硬塞进本册。
2. **跨册重名怎么根治？** 现在 38 处重名。是接受"同名不同册"（靠 path 区分），还是在词表层面加后缀（"轴对称图形（五上）"）？后者对 AI 更友好，但名字变丑、人工检索变难。
3. **"章"这一层够不够？** 五上 9 章 25 节 63 个知识点，平均一章 7 个点。如果按章给候选（每章 5–15 点），候选集刚好合适。但如果某章特别大（比如九年级"二次函数"），仍要再切。
4. **两轮的延迟能不能接受？** 家长批量录 20 道，每道多 5 秒 = 多 100 秒。异步（方案 C）能吸收，但会引入"标签还没到"的状态。
5. **反馈闭环用什么形式？** 人工改标签这件事本身是有信息的（AI 错在哪一类），但记录它需要额外字段和历史表。要不要为"标签修正历史"单独建表，还是只在 `ErrorItem` 上记最后一次来源？

## 7. 给外部模型的提问（可直接复制）

> 背景：一个 K12 错题本应用（Next.js + SQLite，单机 NAS 部署，无向量库、无 GPU）。用户拍照一道题 → 视觉模型一次调用返回：题目转录、答案、解析、学科、错因、1–5 个知识点标签。知识点来自一棵四层树（册 → 章 → 节 → 知识点，数学 595 个知识点、38 处跨册重名）。
>
> 现在的问题：一次调用里任务太多，标签只是 1/8 的输出；模型只交回知识点名字，服务端按名字反查，跨册重名导致挂错册；AI 自造的名字被挂到"册"这一层，形成野节点；人工纠错时没有候选可浏览，只能靠打字猜。
>
> 我的方案是：①先修 bug（学科未知不默认数学、PUT 补齐校验）②把输出协议改成"册 + 章 + 节 + 名字"四段式，服务端按路径定位 ③加"待归类"队列和人工确认锁 ④最后做两阶段：第一轮只让 AI 定位到"学科 + 册 + 章"（不解题、不转录），服务端检索出 20–40 个候选，第二轮纯文本从候选里选编号。
>
> 请评估：这个路线是否合理？特别是：
> 1. 两阶段的第一轮"只定位不解题"，在只有图片输入的情况下，准确率会比"边解题边选标签"更高还是更低？为什么？
> 2. 有没有比"册 → 章 → 节"更好的检索中间层？（比如用教材目录做 BM25，或用题干文本对知识点名做字面匹配）
> 3. 在单机、无向量库的约束下，还有没有更简洁的做法能达到同样效果？
> 4. 跨册重名（同一知识点在不同年级重复出现）在数据建模上应该怎么处理？
> 5. 有没有可能干脆不要"AI 选标签"，改成"AI 只产出题干文本 + 章节猜测，标签由规则匹配 + 人工确认"？
