# 第一批：止血（含高三修复）

## 1.1 高三：映射表与词表对齐

### 现状（事实）

| 位置 | 内容 |
|---|---|
| `src/lib/tag-data/math.ts` 等四个理科 | 顶层节点是 `高三`（单节点，无上下） |
| `src/lib/ai/tag-scope.ts:21` | `12: ['高三上', '高三下']` |
| 结果 | `topNodeNamesUpTo(12)` 返回 6 个名字，其中 2 个库里不存在 |

`getTagTree()` 用 `wantedTops.has(t.name)` 过滤根节点 ⇒ **高三整册被过滤掉，从不进入 AI 清单**。

### 改法

1. `tag-scope.ts`：

```ts
12: ['高三'],   // 高三不分上下，与词表顶层一致
```

2. 新增纯函数（放 `tag-scope.ts`，可单测）：

```ts
/**
 * 「年级/学期」→「词表里的册名」。
 *
 * 为什么需要它：`gradeTerm` 回答的是"她什么时候在读"（高三上/下都真实存在），
 * 而 `bookKey` 回答的是"词表里取哪一册"（高三只有一轮复习，没有下册）。
 * 一个字段不能同时当两个用。
 */
export function bookKeyOf(term: string | null | undefined): string | null {
  if (!term) return null;
  const t = term.trim();
  if (t === '高三上' || t === '高三下' || t === '高三') return '高三';
  return t;
}
```

3. `src/lib/tag-recognition.ts` 的 `findParentTagIdForGrade()`：
   查询根节点前先过 `bookKeyOf()`，避免"高三上"挂不上父节点。

4. `src/lib/ai/tag-service.ts` 的 `getTagTree()` 加一道兜底：

```ts
const roots = all.filter((t) => t.parentId === null && wantedTops.has(t.name));
if (roots.length === 0) return [];
// 【新增】映射表与词表不一致时，不能静默少册 —— 打日志，让下次一眼看见
if (roots.length < wantedTops.size) {
  const missing = [...wantedTops].filter(n => !roots.some(r => r.name === n));
  logger.warn({ subject, grade, missing }, 'wantedTops 与库中根节点对不上，可能有册被漏掉');
}
```

5. 改测试 `src/__tests__/unit/ai/tag-scope.test.ts:38`：

```ts
it('高三 ⇒ 从高一上累到高三（高三不分上下）', () => {
  const names = topNodeNamesUpTo(12);
  expect(names[0]).toBe('高一上');
  expect(names[names.length - 1]).toBe('高三');
  expect(names).toHaveLength(5);
  expect(names).not.toContain('高三上');
  expect(names).not.toContain('高三下');
});
```

6. 新增测试：`bookKeyOf('高三上') === '高三'`、`bookKeyOf('五年级上') === '五年级上'`。

### 验收

```
npx vitest run src/__tests__/unit/ai/tag-scope.test.ts
```
全绿；且新增的 `bookKeyOf` 用例通过。

### 风险与回滚

- 只改常量 + 新增纯函数，不改 UI、不改数据。
- 回滚 = 改回一行。

## 1.2 止血四条的另外三条

### (a) 学科未知时不再默认数学

`openai-provider.ts:215`、`azure-provider.ts:188`、`gemini-provider.ts:199`（三处**完全重复**，同批抽成一个函数）。

改法：把"取清单"这段从三个 provider 里抽到 `tag-service.ts`：

```ts
export async function loadTagListForPrompt(
  subjectKey: string | null,
  grade: number | null,
): Promise<{ tree: TagBranch[]; subjectUsed: string | null }> {
  if (!subjectKey) return { tree: [], subjectUsed: null };  // 不猜
  return { tree: await getTagTree(subjectKey, grade), subjectUsed: subjectKey };
}
```

`subject` 为空时：**不给任何清单**，提示词里写明"学科未知，knowledge_points 只写 UNMATCHED"。

这样处理后，从首页首次拍照的语文题不会拿到数学清单；代价是这一条动线拿不到标签——**宁可不给，也不给错的**。等第三批的待确认队列上线后，这些题会出现在队列里让人补。

### (b) PUT 接口补齐校验

`src/app/api/error-items/[id]/route.ts:700-725`：

- 查重加 `subject`；
- `parentId` 为 null 时**不建**（与 POST 一致），记进 `tagResolution` 的 `matchedBy: 'none'`。

### (c) unmatchedTags 显示出来

POST 返回的 `unmatchedTags` 目前前端不读。改：`batch-pipeline.tsx` 保存后若返回非空，调用一次 toast/提示条：

> 这道题有 2 个标签没能归类（"解决实际问题""线段"），已记下，稍后可在「待归类」里处理。

这一步只是让失败可见，真正的修复在第三批。

### (d) 下游盘点（我先做，不占他时间）

把"标签到底被谁用"数一遍：

```
grep -rn "tags:" src/app/api/practice src/app/api/export src/app/api/paper | ...
```

结论写进第三批开工前的备忘：现在到底是"章"够用，还是真有人消费到"知识点"。这决定第四批的 B 做不做。

# 第二批：交坐标（方案 A）

## 2.1 输出协议

### 改模板

`src/lib/ai/prompts.ts` 两处：

1. `<knowledge_points>` 段**从第 136 行挪到 `<analysis>` 之后**（模型是自回归的，放到最后 = 让它看着自己刚写的解析再选）。
2. 段内容改成：

```
<knowledge_points>
<kp book="五年级上" chapter="第五单元 多边形的面积" section="平行四边形的面积" name="底和高的对应"/>
<kp book="五年级上" chapter="第五单元 多边形的面积" section="平行四边形的面积" name="平行四边形的面积"/>
</knowledge_points>

<book_reason>
仅当 book 与她当前在读的册不同（或无法确定）时填写一句判据，例如"题干出现分数乘整数，属六上"。
相同则留空。
</book_reason>
```

### 必须处理的坑：配置里的旧模板

`config.prompts.analyze` 可能是旧副本（上次 `<mistake_category>` 就是这么静默失效的）。自愈函数 `withRequiredOutputTags()` 只补缺失字段，**不管顺序**。

本批要在 `generateAnalyzePrompt()` 里加一步 `moveKnowledgePointsToEnd(template)`：

```ts
/** 把 <knowledge_points> 整段挪到末尾（含配置里的旧模板） */
function moveKnowledgePointsToEnd(t: string): string {
  const m = t.match(/<knowledge_points>[\s\S]*?<\/knowledge_points>/);
  if (!m) return t;
  const rest = t.replace(m[0], '');
  return `${rest}\n${m[0]}\n`;
}
```

加单测：喂一份"knowledge_points 在中间"的模板，输出里它必须在 `<analysis>` 之后。

## 2.2 解析

`src/lib/ai/knowledge-split.ts` 旁边新增：

```ts
export interface TagRef {
  book?: string;
  chapter?: string;
  section?: string;
  name: string;
}

/** 解析 <kp .../>；解析不出任何一条时返回 []，由调用方降级到旧的逗号切分 */
export function parseTagRefs(raw: string | null | undefined): TagRef[];
```

兼容策略：先试新格式；`[]` 则退回 `splitKnowledgePoints()`，并给所有 ref 标 `legacy: true`（即"只有名字，没有位置"）。

`ParsedQuestion` 增加**可选**字段 `knowledgeRefs?: TagRef[]`（zod 里 `.optional()`）。现有 `knowledgePoints: string[]` 保留不动 ⇒ **前端零改动**。

## 2.3 落库（三级降级）

`src/app/api/error-items/route.ts` 抽出 `resolveTagRefs()`：

```
第 1 级：book + section + name 全匹配 → matchedBy='path'
第 2 级：book + name 匹配         → matchedBy='book-name'
第 3 级：都不匹配                  → matchedBy='none'，不建节点，进 tagResolution
```

**绝对不允许**退回"全局按名字查"——那正是跨册撞车的来源。

新字段（迁移 `prisma/migrations/<时间>_tag_resolution/migration.sql`）：

```prisma
  /// AI 选标签的可追溯结果（JSON 数组）。只用来回答"它选对了没有"，不参与业务查询。
  /// 形如 [{"name":"底和高的对应","tagId":"...","matchedBy":"path"}]
  tagResolution String?
  /// 偏离默认册时 AI 交的判据（一句话）。用来审"它是真读了题还是顺着默认走"。
  tagDeviation String?
```

为什么用 JSON 而不是建关联表：现在只要求"两周后能数出占比"，一条 SQL 扫 JSON 就够；建表会把"标签关联"这套已经很绕的逻辑再翻一遍。

`matchedBy` 取值：`path` / `book-name` / `none` / `legacy`（旧格式）/ `human`（人确认过）。

## 2.4 完成定义（必须能跑，不是"已测试"）

写一个脚本 `scripts/verify-tag-resolution.ts`，输出三行数字：

```
最近 50 道题：tagResolution 非空 50/50
matchedBy 分布：path 38, book-name 7, none 5
偏离默认册的记录中 tagDeviation 为空的：0
```

命令：
```
npx tsx scripts/verify-tag-resolution.ts
```

三条硬标准：

1. 回归表跑一遍，**挂错册 = 0**；
2. 最近 50 条记录 `tagResolution` 非空占比 100%；
3. `book` 与默认册不同的记录，`tagDeviation` 非空占比 100%。

## 2.5 回归表（按我的成本改法）

讨论里说"38 组各拍一道题"，成本过高。拆成两层：

**第一层：静态表，不需要图片**

```ts
// src/__tests__/unit/tag-resolve-regression.test.ts
const CASES = [
  { ref: { book: '五年级上', name: '轴对称图形' }, expectBook: '五年级上' },
  { ref: { book: '二年级上', name: '轴对称图形' }, expectBook: '二年级上' },
  // …38 组重名，每组至少 2 条，覆盖全部册次
];
```
直接测解析函数：喂 `TagRef`，断言命中的 `tagId` 属于期望那册。**跑一次几百毫秒，覆盖全部 38 组。**

**第二层：真图片，6–8 道**

必须包含：
- 3 道高三题（验证第一批的修复）；
- 2 道跨年级复习卷（比如六上卷子里混着五下的题）；
- 2 道"本册但跨章"的题；
- 1 道 AI 大概率归不上的题（验证它敢说 none）。

这批图片只能用他的手机拍，这是**唯一必须他配合的事**。

## 2.6 UI（很小）

- 题目详情页：标签 chip 下加一行灰色小字面包屑 `五年级上 › 第五单元 › 平行四边形的面积`。
  只做展示，不占标签位。
- AI 改了默认册时，同一行前面加一个淡黄小点 + tooltip 显示 `tagDeviation`。

# 第三批：待确认队列（方案 D）

## 3.1 数据

不建新表。查询条件：

```
tagResolution 包含 matchedBy in ('none','book-name','legacy')
```

## 3.2 接口

`GET /api/tags/pending` → 列表（题号、题干前 40 字、AI 原词、候选）
`POST /api/tags/pending/resolve` → `{ itemId, tagName, tagId }`

候选召回（宽松，宁多勿漏）：
1. 去括号补充、去空格、全半角归一后精确匹配；
2. 别名表（先用第一批盘点出的 8 个旧词 + 60 个野节点归纳）；
3. 同册内编辑距离 ≤ 2 的按相似度排序。

## 3.3 页面

`/tags` 加一个 tab「待归类」，每条一行：

```
SX20261031001  平行四边形面积计算…    AI："平行四边型面积"   候选：平行四边形的面积(五上) ▸ 确认
```

确认后写 `tags` 关联 + `tagResolution.matchedBy='human'`。

## 3.4 备注字段

确认时可选填一句话（如"这题其实是三下的"），存进 `tagDeviation`（复用，不新建列）。

# 第四批：观测与决策（不写代码，只出数）

A 上线两周后交两个数：

1. `matchedBy=path` 在本册题 / 跨册题上的占比（分列，不分列会虚高）；
2. `tagDeviation` 与所选 `book` 不一致的比例（判据是否被"编"）。

加上第一批 (d) 的下游盘点结论，三个数决定 B 做不做：

| 下游有知识点级消费者？ | path 命中率 | 结论 |
|---|---|---|
| 没有 | 任何 | **B 不做**，A + D 足够 |
| 有 | 高 | B 的边际成本只剩候选集和第二轮，值得做 |
| 有 | 低 | 先修第 1 轮定位，不要加第二轮 |

# 第四批 · 下游盘点（2026-10-31 已完成）

外部模型提的前提问题："到底有没有人在用知识点这一级？"

盘点结果：**有，但只有三处**。

| 消费点 | 用到哪一级 | 说明 |
|---|---|---|
| `src/app/api/practice/generate/route.ts:33` | **知识点名（字符串）** | 举一反三 / 同类题生成，读 `knowledgePoints` 这个 JSON 字段 |
| `src/app/api/tags/stats/route.ts` | 标签（按关联） | 标签页的"使用频率 Top 20" |
| `src/app/api/export`、`[id]/export-obsidian` | 标签名 | 导出到 Obsidian 时带标签 |
| `src/components/error-item-card.tsx` | 标签名 | 错题卡片上的 chip |

复习卷（`review-volumes`）读的是**卷快照**里的年级/学科，不消费知识点。

**结论**：知识点级消费者确实存在（练习生成 + 统计），所以方案 B 不是白做。但它值不值得做，仍然取决于 A 上线后 `matchedBy=path` 在本册/跨册两类题上的占比 —— 这一点不变。

> 另：`practice/generate` 读的是 `knowledgePoints` 字段而不是 `tags` 关联。
> 这次改造**保留了该字段**（写入解析后的名字），所以它不受影响。
> 若以后要按"章"出题，读 `tagResolution` 里的 `book`/`section` 即可，不必再解析名字。
